# Safe Rust compiler clone analysis and conversion plan

Build a safe Rust implementation of all nine tools that preserves the current
compiler's observable behavior and generated bytes. Use the assignments to
establish each language and tool contract, then impose stricter differential
checks against a frozen C++ implementation. The final acceptance test is that
Rust compiles the existing C++ compiler sources into the same objects and
executable as the C++ compiler's self-build.

This is an implementation plan, not a completed port or a certification that
the current checkout passes its suites. The source baseline analyzed here is
`72181d97e2a8b90af16229a328fc8e72bfe71f4b`. Implementation should begin by
reproducing and freezing that baseline. Keep the C++ implementation buildable
throughout the conversion. This maintainer document stays outside
`scripts/student_export_documents.txt`; preserve [NOTICE](../NOTICE) and
inherited attribution in translated material.

## What exact compatibility requires

Use Linux x86-64, ELF, the existing target data model and Itanium ABI as the
first acceptance configuration. Pin the host compiler, standard library,
headers, linker, runtime libraries, locale and build flags. Other supported
host configurations need their own baseline; comparing artifacts produced
under different configurations is a separate claim.

The target is this implementation's complete supported surface, including
hosted GNU/Clang extensions and accepted later-language features. Restricting
the port to textbook C++11 would miss behavior already used by hosted headers
and self-compilation. Examples include the dialect controls in
[PreprocessorOptions](../dev/src/preprocess/preprocessor.h), extended floating
types in [literal scanning](../dev/src/lex/number_literal.cpp), and structured
binding facts in [SemanticGraph](../dev/src/sema/semantic_unit.h).

| Surface | Acceptance requirement |
| --- | --- |
| All nine command-line tools | Same options, defaults, input handling, output destinations, successful output bytes and exit status. Preserve option precedence, dependency-file behavior and relevant driver queries. |
| Rejected input | Same acceptance/rejection decision, exit status and deterministic diagnostic text and locations. Course grading generally ignores diagnostic wording; the clone comparison must check it separately. |
| AST, types, semantics, ABI names, LowIR and MIR | Raw output equality to the frozen C++ tool in the same mode, in addition to the assignment's normal comparison. |
| Native output | Identical complete object and executable bytes, including metadata, padding, relocation order, symbols, unwind tables and requested debug information. Execution and host-interoperation tests must also pass. |
| Optimization | Same transformations, ordering, thresholds and tie-breaks at `-O0` through `-O3`, plus the current aliases of those options. Equivalent code is insufficient for byte identity. |
| Statistics | Preserve the interface and counter meanings. Compare deterministic work counts where they describe the same work; measure implementation-specific allocation counts, elapsed time and RSS rather than requiring identical numbers. |
| Environmental inputs | Supply identical effective paths, include files, predefined macros, clock values and host configuration. Record these as inputs rather than removing their effects from output comparisons. |

Distinguish rejection from a signal, timeout, panic or internal compiler
failure. A crashing candidate has not matched a rejecting oracle. Unstable
oracle output or behavior caused by undefined behavior in the compiler itself
must be reduced and resolved before freezing that case; it cannot define a
reproducible Rust contract. Correctness fixes to the C++ baseline should be
separate changes with a new recorded baseline, never silent reference updates.

### The final compilation diagram

Let `S` be one frozen C++ source tree, `H` the real host C++ compiler, and `R`
the Rust compiler executable built with a pinned Rust toolchain. Each arrow
below means compiling the same sources with the same effective options and
linking through the same host link recipe:

```text
H(S)   -> C0       host-built C++ seed
C0(S)  -> C1       C++ self-build
C1(S)  -> C2       C++ inception build
R(S)   -> CR       C++ compiler built by Rust
CR(S)  -> C3       inception from the Rust-built C++ compiler

Required: C1 == C2 == CR == C3, byte for byte,
          with the same equality for every corresponding object.
```

The Rust executable `R` is a C++ compiler implemented in Rust. Its executable
bytes need not equal `C1`, and this project does not require it to compile Rust.
The equality being proved is its compilation of the original C++ sources.
[PA34](../pa34/README.md) already requires `C1 == C2`; extend that proof with
the Rust-produced branch. Retain behavior tests because a fixed point alone
does not establish compiler correctness.

## Architecture and size of the existing implementation

The architecture in [spec.md](../spec.md) is already suitable for a Rust port:
one in-process pipeline, typed phase boundaries, compact identities, explicit
demand, per-function backend ownership and direct ELF emission. Preserve those
properties while replacing C++ memory-management techniques.

The baseline has 388 `.cpp` and `.h` files under `dev/src`, containing 199,307
physical lines, including comments, blank lines and scaffolds. These are scope
measurements, not the audit's lines-of-code metric, and exclude tool entry
points under `dev/`.

| Area | Files | Physical lines | Main conversion concern |
| --- | ---: | ---: | --- |
| `lex`, `preprocess`, `types` | 62 | 10,843 | Source bytes, token demand, macro state, literal bits and dialects |
| `syntax` | 32 | 15,266 | One source-faithful tree, parser checkpoints, deferred bodies |
| `sema` | 86 | 63,128 | Canonical identity, lookup, templates, constant evaluation, demand |
| `abi` | 11 | 5,617 | Typed ABI graph, substitutions and exact Itanium spellings |
| `lower` | 37 | 41,587 | Consuming recorded facts, cleanup order, layouts and emission order |
| `lowir` and three root model headers | 29 | 8,566 | Typed vocabulary, function storage and text adapters |
| `opt` | 30 | 20,620 | Pass scheduling, preserved analyses and exact rewrite choices |
| `native` | 81 | 30,945 | ABI classification, register allocation, encoding, objects and runtime |
| `driver`, `support` | 20 | 2,735 | Explicit configuration, errors, storage, telemetry and tool integration |

Semantic analysis and lowering account for over half the physical lines.
This is a substantial compiler rewrite. Treat lexer and parser progress as
early integration evidence, not as a reliable percentage of completion.

Concrete implementation boundaries to carry across:

- [SyntaxUnit](../dev/src/syntax/syntax_unit.h) owns source-related state,
  interning, token spellings and syntax storage. Its parser consumes a pull
  stream. Tool dumps are views of that tree.
- [SemanticGraph](../dev/src/sema/semantic_unit.h) owns interned types,
  indexed names and entity facts; semantic records refer to syntax rather
  than duplicating the whole tree. Dense facts and sparse extension facts
  have different storage needs.
- [Arena](../dev/src/support/memory/arena.h) uses raw allocation, placement
  construction and rewind marks. This is a storage implementation to replace,
  not an interface that requires unsafe Rust.
- [LowIR Program](../dev/src/lowir/program.h) already uses IDs and vectors;
  each `FunctionBody` owns its editable instructions, blocks and operands.
  `DefinitionSink` supports streaming at `-O0`. This is the easiest major
  boundary to port and validate independently.
- [Definition ordering](../dev/src/lower/definition_order.cpp) separates
  semantic demand from presentation order. Preserve its ordering keys and
  ABI-entry ranks, including ties and thunk adjustments.
- [Optimizer scheduling](../dev/src/opt/optimizer.cpp) tracks function
  versions, settled passes and bounded rounds. Port that schedule as well as
  each transformation; changing either can change emitted bytes.
- [The ELF writer](../dev/src/native/object/elf_object_writer.cpp) explicitly
  constructs sections, symbols, relocations and padding. Reproduce that
  serialization instead of relying on another writer's layout conventions.
- [Host environment setup](../dev/src/driver/host_environment.cpp) consumes
  generated host configuration and filters predefined macros. The real host
  supplies configuration and bootstrap linking, not C++ compilation on behalf
  of the candidate.

The tool composition is recorded in
[frontend_source_sets.mk](../dev/frontend_source_sets.mk). Use it to build a
translation ledger: C++ module, Rust owner, phase interface, assignment owner,
parity checks and completion state. Every implementation module and shipped
vocabulary table must have an owner before final signoff.

## Proposed Rust organization

Keep manifests under `dev/` and implementation under `dev/src/`. A practical
layout is a workspace at `dev/Cargo.toml`, member manifests under
`dev/rust/<crate>/Cargo.toml`, and explicit library/binary paths into
`dev/src/rust/<crate>/`. This keeps Rust separate from the retained C++ source
without putting compiler logic in assignment directories.

Start with these crate boundaries, using responsibility-named modules inside
each crate:

| Crate | Contents and permitted dependencies |
| --- | --- |
| `cppgm-support` | Typed IDs, byte storage, target arithmetic, errors and telemetry; no compiler-phase dependency |
| `cppgm-front` | Lexing, preprocessing, syntax, types and semantics; depends on support. Keeping syntax and semantic facts together avoids a cyclic crate dependency. |
| `cppgm-abi` | Canonical ABI graph and encoder; depends on support, accepts typed ABI targets |
| `cppgm-lowir` | Vocabulary, program, builder, validator and explicit text adapters; depends on support |
| `cppgm-lower` | Frontend facts to LowIR, demand/emission scheduling and ABI construction; depends on front, ABI, LowIR and support |
| `cppgm-opt` | LowIR analyses and passes; depends on LowIR and support |
| `cppgm-native` | MIR, selection, allocation, x86 encoding, ELF, runtime and course linker; depends on LowIR and support |
| `cppgm-driver` | Typed invocation and phase orchestration; depends on the phases it invokes |
| `cppgm-tools` | Nine thin entry points, external configuration and diagnostics; invokes shared phase APIs |

The Cargo dependency graph should make it impossible for optimization and
native generation to depend on frontend storage. Keep the ABI fact-file reader
and LowIR text reader as explicit tool adapters; no production phase should
render text to obtain another phase's input.

Install candidate executables into a separate generated tool directory, such
as `obj/rust/bin/`, with the nine existing external names. A Rust target named
`cppgm-driver` can be installed as `cppgm++`. Preserve `dev/`'s C++ executables
and reference routing. Cargo artifacts belong under an isolated `obj/` root.
Do not introduce C++ FFI, a C++ backend library, compiler subprocess fallbacks,
or generated C++ as the implementation of any Rust compiler phase.

### Ownership and representation rules

1. **Use typed indices for graph edges.** Define distinct `ExprId`, `TypeId`,
   `DeclId`, `ScopeId`, `SymbolId`, `BlockId` and `InstId` newtypes. Constructors
   check overflow and reserve any sentinel deliberately. `Option<Id>` should
   replace nullable relationships where practical. IDs belong to one owner;
   prevent cross-unit mixing through private APIs and debug owner checks.
2. **Use owned, flat storage.** Store homogeneous nodes in `Vec<Node>` or
   safe slabs, with IDs remaining valid across vector growth. Store child
   lists in owner-managed vectors and refer to ranges. Avoid `Box` per syntax
   node, `Rc<RefCell<_>>` graphs, recursive owning edges and deep `Clone`.
   Dropping a translation unit must not recursively walk its syntax graph.
3. **Keep borrows short.** Read a small copyable descriptor or child ID, end
   the borrow, then recurse or mutate. Split independent stores into separate
   fields. Use safe slice operations for disjoint mutations. Do not clone a
   tree, introduce dynamic borrow checks or use raw pointers just to satisfy
   the borrow checker.
4. **Make parser rollback transactional.** A checkpoint records token-window
   position, relevant vector lengths and reversible parser-name changes.
   Speculative IDs cannot escape before commit. Rewind all associated facts
   and indexes together; truncate storage only after removing their edges.
   Test nested failure/commit and slot reuse. Stable canonical identities
   must not be recycled by a speculative parse rollback.
5. **Keep source as bytes.** Own immutable file buffers and spelling pools;
   tokens refer to offsets or interned IDs. Validate UTF-8 and universal
   character names according to the source rules. Do not use lossy conversion
   or Rust `char` indexing as a substitute for byte locations. Preserve
   embedded NUL handling, line splices, presumed locations and path bytes.
6. **Record analysis once.** Facts live on nodes or in dense arrays keyed by
   node ordinal. Sparse extension facts may use maps. Template instances own
   any fact-bearing cloned nodes and share immutable syntax where possible.
   Instantiate retained syntax; never replay the parser.
7. **Represent demand explicitly.** Use states such as `Unstarted`,
   `InProgress`, `Complete(FactId)` and typed failure states. Separate class
   layout, default arguments, bodies, exception specifications and emission.
   Cache only complete typed keys, use immutable parent-linked environments,
   and schedule deferred work on the event that can complete it.
8. **Own IR at its natural lifetime.** At `-O0`, keep the frontend alive while
   lowering and encoding each demanded function, then release that function's
   IR. At optimizing levels, finish typed LowIR, drop frontend ownership,
   optimize, then encode and release one function at a time. Preserve program
   metadata needed for cross-function decisions without retaining dead bodies.

Use `Result` and small error enums for input failures, typed outcomes for
overload rejection/SFINAE, and lazy diagnostic rendering. Preserve the
distinction between invocation, I/O, implementation-limit, language and
internal errors described in [tool_errors.h](../dev/src/support/tool_errors.h)
and [the exception audit](../scripts/audit_compiler_exceptions.pl). Panics are
not ordinary compiler control flow. Do not map a panic to an expected rejection.

### Determinism and numeric semantics

Separate lookup containers from traversal order. Keep explicit source ordinals,
emission sequences, block layouts and candidate-order vectors. Never derive
generated IDs or output order from memory addresses or map iteration. Rust's
default `HashMap` uses randomized hashing; deterministic output must come from
explicit ordering, without replacing all hot maps with ordered trees.
[Rust HashMap documentation](https://doc.rust-lang.org/std/collections/struct.HashMap.html)
describes this behavior. Audit C++ unordered iteration and incomplete sort keys
as potential baseline instability before choosing equivalent Rust algorithms.

Target arithmetic needs its own module, shared by literal reading, semantic
constant evaluation and optimizer folding. Use explicit widths, signedness,
checked conversions and deliberate wrapping or overflow detection according
to the operation being modeled. Check shifts and signed division edge cases.
Rust debug/release overflow differences must never define C++ semantics.

Floating point is an early feasibility gate:

- The C++ implementation asserts a 16-byte storage format with an x87
  64-bit significand. Rust's numeric types do not provide that x87 format;
  ordinary `f64` is insufficient, and binary128 is a different format.
  See [Rust numeric types](https://doc.rust-lang.org/reference/types/numeric.html)
  and [LowIR literals](../dev/src/lowir/literals.cpp).
- Implement explicit binary16, binary32, binary64, x87 extended, binary128
  and bfloat behavior wherever the existing compiler supports it. Represent
  bits and rounding modes explicitly, using safe integer/limb arithmetic.
  Match existing precision changes and intermediate rounding, not merely
  an idealized evaluation of the mathematical expression.
- Match decimal and hexadecimal parsing, halfway cases, subnormals, signed
  zero, infinities, signaling/quiet NaNs, payloads, integer conversions and
  overflow/rejection rules. Zero x87 storage padding exactly as the source
  scanner does. Keep symbolic addresses in constant evaluation as typed
  object identities plus offsets, never host pointers.
- Port the existing interchange parser's algorithms where useful. Separately
  reproduce LowIR's 20-significant-digit spelling, the conditional 21-digit
  x87 form and hexadecimal subnormal spelling. Rust's default float formatter
  would change these outputs.
- Validate this module through PA2, PA8, PA16 and PA32 surfaces, plus focused
  generated boundary values. A pure Rust numeric dependency is acceptable
  only after verifying its formats, rounding and licensing; selecting one
  does not discharge the differential tests.

All project-authored Rust must use `unsafe_code = "forbid"`, including helper
crates and build tooling. This permits safe standard-library APIs and audited
dependencies whose internals may use unsafe code; it does not claim the Rust
runtime or dependency graph contains no unsafe implementation. Keep that graph
small and pinned. Serialize target data with explicit endian operations and
initialized byte buffers, not native Rust struct layouts, `transmute`, packed
references, FFI or inline assembly. Emitting x86 instruction bytes is safe
Rust data processing; target C++ unwinding is generated metadata, not Rust
unwinding through foreign frames.

## Validation infrastructure before conversion

Create a frozen oracle from the analyzed C++ commit and immutable copies of all
nine host-built tools. Record hashes of sources, fixtures, generated host
configuration, compiler binaries and toolchain/runtime inputs. Keep source
changes and reference regeneration separate from the port.

The tool manifest must name `pptoken`, `posttoken`, `ppexpr`, `preproc`,
`cppgm++`, `abimangle`, `lowir`, `lowiropt` and `lowir2native`. Preserve
`dev/frontend_source_sets.mk` for the C++ builds and audit Cargo's corresponding
tool composition; do not treat shared-phase completion as proof that every
entry point links and exercises it.

The normal solution references track tools built from `dev/`; they must not
accidentally become the candidate's outputs. Preserve tracked `.ref*` files and
pin every executable used as a reference, including native execution helpers.
[TESTING_AND_REFERENCES.md](../TESTING_AND_REFERENCES.md) distinguishes the
solution checkout from the downloadable student references.

Add a maintainer runner under `scripts/` that accepts separate oracle and
candidate tool manifests. It should enumerate the lanes from each assignment's
Makefile, invoke the existing runners and checkers, and write artifacts to a
separate run directory or disposable checkout. A manifest records absolute
executable paths and hashes for every tool; fail if any candidate slot resolves
to the oracle by mistake. Log actual invocations so a passing test demonstrates
which implementation performed each phase.

Existing selectors can support the first milestones:

```sh
# Run from the repository root after building the named Rust executable.
make -C pa1 test CPPGM_TEST_APP="$(pwd)/obj/rust/bin/pptoken" \
  CPPGM_SKIP_DEV_REBUILD=1 CPPGM_TEST_RUNNER=0

make -C pa8 test CPPGM_TEST_APP="$(pwd)/obj/rust/bin/lowir" \
  NATIVE_REFERENCE_APP="$(pwd)/obj/rust-oracle/bin/lowir2native" \
  CPPGM_SKIP_DEV_REBUILD=1 CPPGM_TEST_RUNNER=0

CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 make -C pa10 test \
  CPPGM_TEST_APP="$(pwd)/obj/rust/bin/cppgm++" \
  NATIVE_REFERENCE_APP="$(pwd)/obj/rust-oracle/bin/lowir2native" \
  CPPGM_SKIP_DEV_REBUILD=1 CPPGM_TEST_RUNNER=0
```

PA32 needs both `LOWIROPT_APP` and `CPPGM_DRIVER_APP`; PA33 needs
`LOWIR2NATIVE_APP` and `CPPGM_DRIVER_APP`. Debug wrappers, control checkers and
PA35 also have tool selection paths that must be routed explicitly. Root
`make test-report` is not currently a universal tool-manifest interface. Add
one coherent routing adapter rather than assuming that overriding one variable
replaces all nine tools. Run `make test-harness` after changing that routing.

Initially use ordinary process execution and disable batch behavior explicitly
where the runner selects it. Later implement and test the existing worker
protocol, including status framing, stderr, working directory, timeouts and
request isolation. Process orchestration belongs to test tooling; no worker
may invoke the C++ implementation to supply a Rust result. Run both ordinary
and batch paths before completion, including good/bad/good sequences to detect
state leakage between translation units.

### Three checks for every completed milestone

| Check | What it establishes |
| --- | --- |
| Existing assignment checks | Required behavior, negative cases, controls, host interoperability and quality envelopes |
| Exact differential checks | Raw text, diagnostics, ABI names, object bytes and native executable bytes match the frozen implementation |
| Representation and scaling checks | Typed boundaries, bounded token retention, correct rollback, one successful computation per fact, and no accidental allocation or complexity regression |

Run every earlier completed assignment after each milestone. A partial port
may use the frozen native tool to execute a frontend result in the test
harness, as PA8 and PA10–PA23 already do. Record that as frontend validation;
it is not evidence that Rust's backend is complete. Once both sides exist,
test Rust-to-Rust end to end and cross combinations at the explicit LowIR
boundary to locate faults.

Normal comparators can trim whitespace, normalize names or compare structural
properties. Even `CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1` is not a substitute for a
raw byte comparison of every artifact. Preserve original outputs before any
normalization. For objects, compare bytes first; use section/symbol/relocation
and disassembly diffs only to explain a failure. Do not strip, relink,
canonicalize or discard differing sections to turn a failure into a pass.

Keep the two LowIR dialects distinct. The current `cppgm++ --emit-lowir`
selects host-object facts when the output ends in `.lowir` and an explicit
debug-level option is supplied, including `-g0`. A plain course LowIR dump,
even with `--hosted`, is a different view. Use PA32's existing object-roundtrip
recipes and preserve those exact options when locating source-to-object
differences; see [run_emit_lowir_mode](../dev/cppgm++.cpp).

Use bounded generated programs and metamorphic checks in addition to the
fixtures: LowIR parse/write/parse, direct object versus object-LowIR roundtrip,
all optimization levels versus `-O0` behavior, and repeated compilations with
different allocator/hash/process conditions. Compare source programs with the
host only where the course and host contracts agree and the program has
defined behavior. Use clang as the ABI spelling cross-check under
[the repository naming policy](../TESTING_AND_REFERENCES.md#symbol-names).

Promote reduced language regressions into the earliest owning `paN/tests/`
cluster and an executed lane. Read that handout in full before implementing or
changing its behavior. Keep Rust storage and audit unit tests with their
Rust/script owners. `student.tests/` is for temporary reproducers, not required
coverage. Keep solution-specific code-shape checks in the existing regression
lanes; do not change student grading contracts to enforce clone identity.

backend subset, even though full PA24 acceptance comes later. After hosted

layout or declaration-order differences. Repeat at each optimizing level as
its pipeline becomes complete.

PA34's early ladder has an important dependency: rebuilding `pptoken` through
`preproc` is smaller, but PA5's `--emit-ast` tests still require building the
entire C++ `cppgm++` implementation. A Rust frontend that passes PA5 fixtures
is not yet able to perform the PA34-through-PA5 bootstrap.

## Clippy and file audit policy

Use a pinned stable Rust toolchain with the 2024 edition, rustfmt and Clippy.
The environment inspected for this plan has Rust/Clippy 1.98.0; that is a
concrete initial pin, not a requirement to track the newest release. Record
the supported version in workspace metadata and `rust-toolchain.toml`, commit
`Cargo.lock`, and run locked builds. Audit all supported feature configurations,
including telemetry disabled; features must not select different language
semantics.

Use workspace lint inheritance in every member, with an audit that fails if
a member omits `[lints] workspace = true`. Cargo supports inherited workspace
lints as documented in
[the Cargo workspace reference](https://doc.rust-lang.org/cargo/reference/workspaces.html#the-lints-table).
An initial policy for `dev/Cargo.toml` is:

```toml
[workspace.lints.rust]
unsafe_code = "forbid"
unused_must_use = "deny"
unfulfilled_lint_expectations = "deny"

[workspace.lints.clippy]
all = { level = "warn", priority = -1 }
pedantic = { level = "warn", priority = -1 }
unwrap_used = "deny"
expect_used = "deny"
panic = "deny"
todo = "deny"
unimplemented = "deny"
dbg_macro = "deny"
exit = "deny"
mem_forget = "deny"
large_stack_arrays = "warn"
large_stack_frames = "warn"
too_many_lines = "warn"
excessive_nesting = "warn"
```

Set these values in `dev/clippy.toml`, and set `CLIPPY_CONF_DIR` explicitly in
the lint target so command working directories cannot change the policy:

```toml
too-many-lines-threshold = 240
excessive-nesting-threshold = 6
allow-unwrap-in-tests = true
allow-expect-in-tests = true
allow-panic-in-tests = true
```

Enable `all` and `pedantic` from the start and review local exceptions rather
than accumulating warnings. Select restriction lints individually; the Clippy
documentation advises against enabling that entire group. With the proposed
toolchain, CI can use `CARGO_BUILD_WARNINGS=deny`; an older-toolchain variant
uses `-- -D warnings`.
[Clippy usage](https://doc.rust-lang.org/clippy/usage.html)

Use narrow `#[expect(lint, reason = "...")]` attributes when an actual,
documented exception is needed, and fail unfulfilled expectations. Rust
supports reasons and reports stale expectations as described in
[lint levels](https://doc.rust-lang.org/rustc/lints/levels.html). An exception
must not waive the independent file audit. Avoid crate-wide exemptions for
casts, complexity or dead code, and never exclude implementation with
`cfg(clippy)`. A reviewed internal-error function may need a narrow panic
exception; user-input failures must still use typed errors.

Apply suggestions with architectural judgment. For a large enum, prefer
separate typed payload storage when boxing would allocate every hot node.
Use `TryFrom` for sizes/offsets and an explicit target-arithmetic operation for
intentional truncation. Keep indexing inside private typed-store APIs with
clear invariants; blanket `indexing_slicing` or arithmetic restrictions can
produce noise without proving those invariants. Do not mechanically rewrite
float comparisons, evaluation order or clones in ways that alter the oracle's
observable behavior. Helpers should own coherent work, not just shorten a
function enough to pass a lint.

### Matching the repository audit

[cppgm_file_audit.pl](../scripts/cppgm_file_audit.pl) recognizes C/C++ file
extensions. A pass from it does not audit Rust. Add a Rust-aware companion
audit, with tested lexical handling of nested comments, raw strings,
attributes, closures, impl methods and macros. Use syntax spans and a code-line
mask, not a regex that counts braces inside strings. Keep its check policy
aligned with the C++ audit and test threshold boundaries.

| Existing audit requirement | Rust enforcement |
| --- | --- |
| Source file at most 3,000 code lines | Same hard limit for implementation `.rs` files; exclude blank/comment-only lines, not attributes or declarations |
| Header 2,400; internal header 1,800 | Rust has no headers. Register interface/vocabulary modules with a 2,400 cap and internal model/state modules with a 1,800 cap; all other implementation modules retain 3,000. Validate roles so renaming cannot evade a cap. |
| Function at most 240 code lines | Companion audit is authoritative; Clippy `too_many_lines` at 240 is an additional check |
| Dispatch function at most 360 with at least 8 case labels | Rust analogue: at least 8 real `match` arms in cohesive dispatch code, at most 360 code lines. Require a reviewed local Clippy expectation and audit verification; no global 360 threshold. |
| Nesting warning above 6, failure above 8 | Count function-relative nesting in the companion audit. Clippy threshold 6 supplies earlier feedback but may count differently. Warnings fail CI unless narrowly justified; the hard cap remains 8. |
| No mechanical splits or implementation includes | Reject numbered `part`/`chunk`/`split` files and equivalent patterns; normal `mod` ownership is allowed. Forbid `include!` as an implementation-fragment escape. |
| Catch-all files, repeated stems, duplicate blocks | Preserve warnings for catch-all files over 250 physical lines, 7-or-more related stems, and duplicate windows of 28 normalized code lines with at least 240 characters. Review vocabulary repetition separately from copied algorithms. |
| No compressed code | rustfmt plus checks for the current density limits: 24 semicolons, or 900 characters with score 28, or 1,600 characters with score 18. Translate the control-keyword score to Rust and test it. |
| No environment reads in compiler implementation | Ban `std::env` reads and environment macros in phase modules, including aliases/reexports. Capture external configuration only at the tool/build/test boundary and pass typed options. No hidden configuration through dependencies. |
| No external compiler, test answers or hosted-library shortcuts | Audit process APIs, fixture/reference paths and embedded executable scripts. Preserve detection of hosted-private-name special cases. Required builtin vocabulary is explicit and reviewed. |
| Scaffolds and generated tables | Rust translations are implementation and are audited. Share enum/spelling tables with writers and readers; verify completeness and actual use. Generated code is not a blanket exemption. |

Clippy supplies configurable function-length and nesting checks, but not this
whole policy. See its
[configuration table](https://doc.rust-lang.org/clippy/lint_configuration.html).
The companion audit must prevent moving oversized functions into macros,
closures, generated files or ignored modules. Allow generated immutable
vocabulary only through a manifest with provenance and checks of its generator;
never use it to conceal compiler logic.

Port the architecture checks too: crate/module dependency direction, complete
tool composition, LowIR vocabulary/contract coverage, builtin registry tables,
absence of textual phase transport, and typed error handling. Keep the C++
audits running while that implementation remains in the tree. The existing
scaffold dependency-file check cannot by itself prove that Rust consumes its
translated vocabulary.

After the workspace exists, the Rust gate should include:

```sh
cargo fmt --manifest-path dev/Cargo.toml --all -- --check
CLIPPY_CONF_DIR="$PWD/dev" CARGO_BUILD_WARNINGS=deny \
  cargo clippy --manifest-path dev/Cargo.toml --workspace --all-targets \
  --all-features --locked
cargo test --manifest-path dev/Cargo.toml --workspace --locked
cargo test --manifest-path dev/Cargo.toml --workspace --release --locked
```

Add the companion audits and explicit supported feature-matrix commands to
that gate. Keep `target` output isolated through the build configuration. Test
Rust implementation files with rustfmt; never reformat assignment fixtures or
benchmarks. Meaningful unit/property tests should target storage invariants,
arithmetic and phase contracts, while the assignment harness remains the main
behavioral oracle.

## Making PA34 prove byte identity

Implement a maintainer bootstrap comparator that reuses PA34's source lists
and compile/link recipes. It must identify objects by logical source name,
not directory enumeration, and fail on a missing or extra object. Include
entry objects, shared phase objects and the batch-runner object selected by
the configuration. Record every command, input digest and output digest.

The existing default bootstrap is:

```sh
make build CXX=g++ CPPGM_HOST_CXX=g++
make -C pa34 test-through-pa5 CXX=../dev/cppgm++ CPPGM_HOST_CXX=g++
make inception CXX=g++ CPPGM_HOST_CXX=g++
```

These validate the C++ branch. The new comparator must additionally drive the
same PA34 source list with Rust as `CXX`, keeping `CPPGM_HOST_CXX` a real host
compiler. Pass `INCEPTION_COMPILER_FLAVOR=selfhost` explicitly for the Rust
branch: the current Makefile otherwise recognizes only the specific
`../dev/cppgm++` path as that flavor. Preserve the default `-O3` bootstrap
flags and runner defines unless testing a separately recorded configuration.

There is a path trap in the current
[PA34 Makefile](../pa34/Makefile): `INCEPTION_OBJ_ROOT_BASE` determines the
embedded `CPPGM_DEFAULT_OBJECT_ROOT` macro as well as storage locations.
Giving C++ and Rust different values changes the C++ program being compiled.
Keep that logical base identical and use `INCEPTION_OBJ_ROOT` and
`INCEPTION_BIN_ROOT` to isolate physical artifacts, or add a dedicated common
embedded-default override to the bootstrap harness. Keep
`INCEPTION_GENERATED`, source/include spellings and generated configuration
identical too. Verify the expanded compile commands before starting the builds.

Changing `INCEPTION_OBJ_ROOT` alone does not settle every path difference:
check `-MF`/`-MT`, current directory, `__FILE__`, debug compilation directories,
temporary paths and host link commands. If a relevant path is embedded,
replay each branch sequentially at the same logical path and copy artifacts
out between runs. Isolate stored outputs without changing program inputs.

Acceptance procedure:

1. **Establish repeatability.** Compile representative ordinary, template,
   floating, EH and debug inputs twice with `C0`. Resolve any output
   nondeterminism before comparing Rust. Freeze effective date/time macros;
   `SOURCE_DATE_EPOCH` must not be assumed to work because the current entry
   point obtains `__DATE__` and `__TIME__` from the clock. Use existing macro
   controls or an explicit common harness clock input, validated on both tools.
2. **Build the existing fixed point.** Build `C1` with `C0`, `C2` with `C1`,
   compare every corresponding object and final executable, and preserve the
   artifacts immutably. A failed C++ inception is a baseline failure to fix.
3. **Build from Rust.** Compile every C++ source with `R` into a fresh object
   generation. Compare each object immediately against `C1`'s corresponding
   object before linking. Do not reuse a successful C++ object for a source
   Rust failed to compile.
4. **Link identically.** Use the same host executable, object order, flags,
   runtime/CRT libraries, allocator selection and effective link path. Compare
   `CR` with both `C1` and `C2` using `cmp`; store SHA-256 values for the run
   record. Diagnose build IDs and other metadata rather than stripping them.
5. **Rebuild from the result.** Use `CR` to compile `S` again, producing `C3`,
   with fresh objects. Require the same object and executable equality. This
   also exercises the rebuilt compiler as a compiler.
6. **Exercise all tools.** Run PA34's through-PA4, through-PA5, through-PA8
   and through-PA33 ladder as applicable. Build and compare the other eight
   original C++ tools using Rust too. Run PA1–PA33 with the rebuilt tools,
   then debug-info and PA35 correctness checks.
7. **Repeat from a clean build.** Use a fresh artifact root with identical
   logical inputs. Check ordinary and batch configurations independently.
   Expand to another host/toolchain configuration only with its own frozen
   comparison branch.

When an object differs, find the earliest divergent boundary: preprocessing,
syntax, semantic choices, ABI graph/name, typed LowIR, optimized LowIR, MIR,
encoding, then ELF layout. Diagnostic dumps may expose typed IDs and ordering
keys in audit builds, but must not become production transport. Reduce the
first mismatch into the correct assignment lane. Do not postpone thousands
of unexplained object differences until the final link.

## Performance and release gates

Exact generated bytes do not imply equal compiler speed or memory use. Measure
Rust separately from the C++ compiler it produces. A byte-identical `CR` has
the same generated program as `C1`, but the Rust process doing the compilation
has different storage, runtime and host-generated code.

Use the existing fixed inputs in `benchmarks/`, PA30 heavy headers, PA34's
source set and [PA35's frozen workload](../pa35/README.md). At each expensive
subsystem milestone, retain phase timings, peak RSS, source/token/IR sizes,
candidate counts, specialization work and allocation measurements. Look for
accidental quadratic behavior before optimizing constant factors.

For wall-time comparisons, freeze both compiler binaries and input trees, run
A/A calibration followed by paired ABBA blocks, retain every observation and
verify output equality. Measure cold and warm conditions separately when
relevant, using the same machine and runtime environment. Use
[validate_perf_regression.py](../scripts/validate_perf_regression.py) for its
supported macOS hardware-counter gate; do not claim that gate ran on Linux.

PA35 is not an active conversion assignment: its purpose is to improve code
generation and compiler performance, while this port must preserve generated
bytes. Retain its correctness generators and frozen workload identities as
additional validation inputs. Measure Rust compile speed, memory and scaling
separately; do not impose the inherited GCC instruction or seed/self ratios
on a rustc-built executable. PA32 and PA33 remain mandatory exact ports of the
existing optimizer/backend, including their ordering and tie-break policies.
Use the original C++ source and `CR` for PA34's code-generation comparison.

For compiler changes, keep the repository's required C++ checks:

```sh
CPPGM_LOWIR_DIRECT_TEXT_COMPARE=1 make test-report
make test-debuginfo
make -C pa34 test-through-pa5 CXX=../dev/cppgm++ CPPGM_HOST_CXX=g++
make audit-lowir-contract audit-compiler-layout audit-compiler-exceptions \
  audit-frontend-source-sets audit-builtin-registry-tables \
  audit-scaffold-usage audit-scaffold-spellings audit-clang-format
perl scripts/cppgm_file_audit.pl --paths dev
python3 scripts/audit_pa_feature_placement.py --fail-on-early
```

Run the corresponding Rust-routed checks for completed milestones. Run the
cross-implementation inception after bootstrap behavior changes; reuse selected
PA35 correctness workloads after lowering, optimizer or backend changes.
Run `make test-harness` for harness/export changes. The unmodified C++ project
retains its own release workflow; its PA35 calibration is not a Rust clone
acceptance gate. Keep Rust measurements separate from generated calibration.

The conversion is complete only when:

- All nine Rust tools pass every applicable course, control, regression,
  hosted and debug lane, plus exact differential checks and rejection tests.
- Every C++ implementation responsibility has a Rust owner, with no unfinished
  path, C++ fallback, test recognition or reference dependency in production.
- Safe-code, Clippy, formatting, source-shape, architecture, registry and
  placement gates pass; supported features preserve output identity.
- Clean bootstrap runs prove `C1 == C2 == CR == C3` for every object and final
  compiler, with the additional eight tool builds and ladder tests complete.
- Rust throughput, memory and scaling measurements are recorded against frozen
  workloads; any agreed resource limits hold. The retained C++ build and
  inception workflow remain valid, without requiring new code generation.

The first implementation change should therefore freeze and verify the oracle,
add explicit candidate routing, and establish the Rust workspace/audits. Follow
it with the numeric and typed-storage foundations and PA1. This yields a small
executable milestone without committing the rest of the compiler to untested
numeric or ownership assumptions.
